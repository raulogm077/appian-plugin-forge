# Reglas de validación, con su fuente

Cada regla vive en un script; esta tabla es el índice que permite responder «¿por qué me
rechazas esto?» con su fuente primaria. Las fuentes son de cuatro clases, y cada fila dice cuál
es la suya: la documentación de Appian (con la página y, cuando la hay, la cita literal en
inglés), la política del AppMarket, el SDK `com.appian:appian-plug-in-sdk:26.3` inspeccionado
con `javap`, o la coherencia interna del propio forge cuando la regla es de diseño propio.

## Capa 1A — reglas del framework de Appian (`R-F01`–`R-F15`, `scripts/verificar_framework.py`)

| ID | Qué comprueba | Fuente | Consecuencia si se incumple |
|---|---|---|---|
| `R-F01` | El valor **efectivo** de `paletteCategory` (leído del bytecode, no si viene de una constante con nombre disciplinado) es uno de los cuatro válidos en 26.x. | *Smart Service Plug-ins > Annotations on the class > @PaletteInfo annotation*: *"Since version 22.2, only four category values are supported: Workflow, Automation Smart Services, Deprecated Services, and Hidden. Any other value will be mapped to Automation Smart Services."* Tres de las siete constantes de `PaletteCategoryConstants` (`APPIAN_SMART_SERVICES`, `STANDARD_NODES`, `INTEGRATION_SERVICES`) compilan pero se remapean: sus valores están leídos con `javap -constants` sobre el SDK 26.3. | El smart service despliega sin error mostrado, pero Appian lo reclasifica en silencio a «Automation Smart Services»: aparece en una paleta distinta de la diseñada y nadie lo encuentra donde se esperaba. |
| `R-F01b` | Que el **nombre** de cualquier anotación de conveniencia de paleta presente en el bytecode (`@DocumentManagement`, `@AutomationSmartServicesDocumentManagement`, `@WorkflowActivities`…) sea de familia segura: prefijo `AutomationSmartServices` o `Workflow`, o la suelta `ForumManagement`. No es una regla con identificador propio — vive dentro de `R-F01` y reporta con su misma `regla`. | La premisa de diseño «emitir anotaciones de conveniencia hace imposible por construcción el error de `R-F01`» es **falsa**: de las 32 anotaciones de conveniencia del SDK, 15 hornean justo uno de los tres valores que `R-F01` rechaza (p. ej. `@DocumentManagement` → `"Appian Smart Services"`, `@Activities` → `"Standard Nodes"`, `@DataServices` → `"Integration Services"`); solo 17 son seguras — la familia `AutomationSmartServices*`, la familia `Workflow*`, y `ForumManagement` (fija «Deprecated Services», válida). Confirmado con `javap -v`, anotación por anotación, sobre `com.appian:appian-plug-in-sdk:26.3` (Maven Central). El hecho de que solo cuatro categorías sean válidas en 26.x es el mismo que sostiene `R-F01`. | La cadena de categoría horneada por la anotación vive dentro del `.class` de la propia anotación, en el SDK (`compileOnly`), y nunca llega al bytecode del plug-in — solo el **nombre** de la anotación llega, así que la comprobación por valor de `R-F01` no puede ver este caso. Sin `R-F01b`, seguir al pie de la letra la recomendación oficial «usa anotaciones de conveniencia» puede terminar en la misma paleta equivocada y silenciosa que produce escribir la cadena suelta a mano. |
| `R-F02` | **En smart services**, toda entrada de tipo primitivo Java (`byte`, `short`, `int`, `long`, `float`, `double`, `boolean`, `char`) declara `required = ALWAYS`. Acotada al tipo: `Required` pertenece al framework de proceso y no existe en una `function`, cuyos parámetros no lo declaran — sin acotar, la regla exigía a toda function con un parámetro primitivo un `ALWAYS` que su plantilla no puede emitir. | *Smart Service Plug-ins > Java component > Inputs and outputs*: *"Input methods that take Java primitives must be marked as required. Passing a `null` value to a Java primitive is not possible."* Para un input opcional hay que usar la clase envoltorio (`Boolean` en vez de `boolean`) y tratar el `null` en el cuerpo del método. La misma página, en *Best practices > Deployment issues*, lo enuncia como fallo de despliegue: *"If a node input uses a Java primitive as a parameter, it must be required, or the plug-in fails to deploy."* | **El plug-in no despliega.** Appian rechaza el registro del smart service con el mensaje *"The input [name] represented by the set method [method] is defined to take a Java primitive as a parameter, but is defined as optional. Since no null value can be given for a primitive, the input must be defined as always required."* |
| `R-F03` | Ningún nombre se repite entre el conjunto de entradas y salidas. | *Smart Service Plug-ins > Internationalization > Translation keys*: *"Input and output names must be unique, or deployment fails."* | El despliegue del plugin falla directamente. |
| `R-F04` | Ninguna entrada o salida usa un tipo no inferible: `byte`, `char`, `short`, `float`, `Currency`, `java.util.Date`. | *Smart Service Plug-ins > Java component > Defining data types used by inputs and outputs*: *"The following Java data types are expressly not supported for inferring an Appian data type: `java.lang.Byte, byte, byte[]` · `java.lang.Char, char` · `java.lang.Short, short` · `java.lang.Float, float` · `java.util.Currency` · `java.util.Date`."* La tabla de esa misma sección fija las fechas que sí se infieren: `java.sql.Date` → Date, `java.sql.Time` → Time, `java.sql.Timestamp` → Date & Time. | Appian no puede inferir el tipo SAIL correspondiente; el campo queda mal tipado o no configurable desde el diseñador. |
| `R-F05` | Si el bytecode referencia `useKeywords`, que `application-version min` sea al menos 26.1. | *Function Plug-ins > Annotations > @Function > Using keywords*: *"Because `useKeywords` is not included (and defaults to `false`), the parameter order is used when the function executes."* Y *Function Plug-ins > Best practices > Versioning and upgrading*: *"Keyword support and enum parameters are only available for Appian 26.1 and above. If using either of these features, set the `<application-version min="26.1.0">` in the `appian-plugin.xml` file. This will prevent plug-in deployment to earlier versions of Appian that don't support these features."* | El plugin compila y despliega, pero `useKeywords` no tiene ningún efecto por debajo de 26.1: el paso de argumentos por nombre que se esperaba simplemente no ocurre, sin aviso alguno. |
| `R-F06` | Ninguna clase de tipo `function`/`writer-function` del paquete del plugin declara el mismo nombre de método más de una vez. | *Smart Service Plug-ins > Java component > Inputs and outputs*: *"Overloaded methods are not supported. If two methods have the same name (but different signatures because they take different parameters), only the first encountered is available as an input or output."* La página de funciones no lo enuncia; la regla aplica el mismo criterio a `function`/`writer-function` porque el nombre de la función de expresión sale del nombre del método, y dos métodos con el mismo nombre solo pueden producir una. | Appian solo expone la primera sobrecarga que encuentra; el resto queda invisible, sin ningún error que lo señale. |
| `R-F07` | El bytecode no contiene ninguna referencia a `javax/naming/InitialContext`. | *Function Plug-ins > Parameters, return types, and type conversion* y, con el mismo texto, *Smart Service Plug-ins > Constructor parameters*: *"The only way to access data sources is by injecting the `javax.naming.Context` into your plug-in function constructor. Plug-in functions, smart services, and servlets using `new InitialContext()` will fail when trying to access a data source configured in the Admin Console."* | Fallo en tiempo de ejecución al intentar acceder a cualquier fuente de datos JNDI configurada en el Admin Console. |
| `R-F08` | Si existe una versión anterior desplegada con la **misma** `key` y la firma de entradas/salidas cambió respecto de ella, el contrato debe declarar clave nueva. | *Smart Service Plug-ins > Best practices > Upgrading*: *"Changed Node Inputs/Outputs: You must use a new key. If you overwrite the plug-in, existing nodes may fail. To upgrade a production system, deprecate the previous plug-in."* La misma página recomienda además usar nombre de clase o de paquete distinto, para que ambas versiones convivan mientras haya procesos activos. | **Rompe procesos vivos en producción.** Es la única regla de esta capa cuya consecuencia cae sobre producción y no sobre el propio despliegue: la de peor consecuencia de todas. |
| `R-F09` | El manifiesto no declara el atributo `xmlns`. | Ningún `appian-plugin.xml` de ejemplo de la documentación de Appian (*Appian Suite Plug-ins*, *Smart Service Plug-ins > Configuration files*, *Function Plug-ins > Configuration files*) declara `xmlns`, y no se localiza ningún XSD publicado del manifiesto contra el que validarlo. | Sin evidencia de que rompa el despliegue; se aparta de todos los ejemplos oficiales conocidos sin beneficio comprobado. Por eso es **aviso**, no error. |
| `R-F10` | `plugin.paquete` no empieza por `com.appiancorp.` ni `com.appian.`. | *AppMarket Submission Policies for Plug-Ins*: *"Plug-in packages must not be named `com.appiancorp.*` or `com.appian.*`."* Es en origen una política de AppMarket (capa 1B, `R-A`); se comprueba también aquí porque el dato ya vive en el contrato. | Rechazo en la revisión de AppMarket / Appian Cloud antes de llegar a producción. |
| `R-F11` | El atributo `key` de la raíz `<appian-plugin>` del manifiesto coincide con `plugin.key` del contrato. | Coherencia interna del propio *forge*. Que `key` es un atributo real que Appian lee del manifiesto lo fija la documentación (*Smart Service Plug-ins > Configuration files > Configuring the appian-plugin.xml file*: *"key Attribute: (Required) A Unique identifier for each Plug-in."*); la exigencia de que contrato y manifiesto no diverjan es una decisión de diseño del forge: coherencia cruzada entre el contrato, el manifiesto, el `.properties` y las firmas Java. | Si el manifiesto desplegado no lleva la `key` que el contrato y el certificado documentan, el certificado describe un plugin distinto del que realmente se despliega; cualquier referencia posterior a esa `key` (invocación, dossier, la propia `R-F08` en la siguiente versión) apunta al objeto equivocado. |
| `R-F12` | El manifiesto declara, en el atributo `class` de algún elemento, la clase que el contrato especifica en `clase.nombre`. | Igual que `R-F11`: coherencia cruzada contrato ↔ manifiesto, apoyada en que la documentación (*Smart Service Plug-ins > Configuration files*) fija `class` como el atributo con el que Appian localiza la implementación: *"class: (Required attribute) The class that implements the smart service."* | Appian carga una implementación distinta de la documentada — o no encuentra ninguna clase que coincida —, típicamente por un bug de sustitución en la plantilla que generó el manifiesto. |
| `R-F13` | Ninguna clase del plug-in conserva en su *constant pool* la marca del cuerpo sin implementar que escriben las plantillas (`contrato.MARCAS_SIN_IMPLEMENTAR`). | Coherencia del propio forge: las cuatro plantillas dejan un `UnsupportedOperationException` a propósito para que el andamiaje falle **ruidoso** si alguien lo despliega sin implementar. Esta regla es el otro lado de esa decisión: si el aviso sigue en el bytecode, el plug-in no está hecho. La marca vive en una constante compartida con las plantillas, para que no puedan divergir en silencio. | Sin esta regla, un andamiaje más un test trivial —el paso siguiente que pide la skill— construye con `BUILD SUCCESSFUL` y saca `STATUS: READY_FOR_APPIAN_SUBMISSION`, con cero motivos que lo impidan, sobre un plug-in cuyo `ejecutar()` no hace nada. Ninguna otra puerta mira si el plug-in **hace** algo: miden el tamaño del insumo, no que el trabajo exista. |
| `R-F14` | Los dos ajustes con los que el andamiaje deja a SpotBugs poder fallar siguen como se generaron (`ignoreFailures = false`, `reportLevel = Confidence.valueOf('LOW')`), y **ninguna exclusión activa** de `config/spotbugs/exclude.xml` se queda sin nombrar en `docs/decisiones.md` — **cualquier patrón y en cualquiera de los cuatro tipos**, una a una: firmar una no absuelve a las demás. Un `<Match>` **sin ningún `<Bug>`** es hallazgo aparte: no excluye un patrón, apaga SpotBugs entero para lo que case. Lo mismo un **`<Bug>` sin atributo `pattern`** —`category="SECURITY"`, `code="XSS"` o un `PATTERN` mal escrito— que apaga una familia o un detector entero y no deja nombre que firmar: un `<Match><Bug category="SECURITY"/></Match>` deja READY con FindSecBugs apagado. La firma es **mecánica**: el nombre del patrón tiene que aparecer en `docs/decisiones.md`; si el motivo escrito lo justifica es juicio del revisor (paso 6), no de este script. Y un **BOM** delante de `<?xml`, también: Python lo tolera y **SpotBugs no** —*«Unable to read filter … Content is not allowed in prolog»*, y el build sigue en `BUILD SUCCESSFUL`—, así que las exclusiones escritas no se aplican y nada lo delata. En Windows sale solo, porque `Out-File` escribe UTF-8 con BOM por defecto. Los `<Match>` comentados no cuentan: el XML se parsea, y un comentario no sobrevive al parseo. Mira **los cuatro tipos**, no solo servlets, y **todos los patrones**, no solo `SERVLET_PARAMETER`/`SECSP`: un `exclude.xml` que nadie parsea es el sitio donde una exclusión añadida a mano no la ve nadie. | Coherencia del propio forge, y la única regla que mira **la puerta** en vez del plug-in. `SKILL.md` ya lo prohíbe por escrito —«ni relajar `reportLevel` ni `ignoreFailures`», y «se excluye `SECSP` para que el build pase» es uno de sus Red Flags— y `andamiar.py` refuerza lo segundo dejando esa exclusión comentada con su argumento al lado. Esta regla es quien vuelve a mirar: ninguna otra capa lee esos tres ficheros. | Con el build en rojo, la vía más corta para sacar un `BUILD SUCCESSFUL` es subir `reportLevel` a `MEDIUM` o descomentar `SECSP` con un motivo inventado antes de escribir `ejecutar()`, sin tocar una línea de código del plug-in; ninguna otra regla mira esos ficheros, así que el certificado saldría con más verdes por haber mirado menos. |
| `R-F15` | Si `build.gradle` declara `dependencyLocking` (perfil RIGUROSO), existe `gradle.lockfile` en la raíz. | El cierre de dependencias que promete el perfil. Gradle, en su modo por defecto, no escribe ni exige el lockfile: `./gradlew build` termina en verde sin dejar rastro, y hay que generarlo a propósito con `./gradlew dependencies --write-locks`. | Sin el lockfile, `dependencyLocking` no fija nada y la build no es reproducible: el perfil promete un cierre que no existe, y nada lo echa en falta. |

## Capa 1B — políticas de AppMarket (`R-A01`–`R-A10`, `scripts/verificar_appmarket.py`)

Son los criterios de aceptación publicados por quien nos va a juzgar, en *AppMarket Submission
Policies for Plug-Ins* (https://docs.appian.com/suite/help/latest/Shared_Components.html):
cumplirlos **siempre** sale barato comparado con un ciclo de aprobación de una semana. Se
comprueban sobre **bytecode**, no sobre fuente: un escáner de fuente se evade con un nombre
cualificado o con reflexión, y hasta tiene que partir sus propios tokens en trozos
(`'Service' + 'Locator'`) para no delatarse a sí mismo.

| ID | Qué comprueba | Fuente | Consecuencia si se incumple |
|---|---|---|---|
| `R-A01` | El bytecode no referencia ningún tipo que empiece por `com.appiancorp.` **y** cuyo nombre contenga `ServiceLocator`, salvo en plugins `tipo_plugin == "servlet"`. | *Function Plug-ins > Parameters, return types, and type conversion*: *"This is the only valid method for obtaining a `*Service` within custom function code. Do not call `ServiceLocator.get*`."* *Smart Service Plug-ins > Constructor parameters* repite la misma nota para el código de smart service. **Excepción de servlets expresa**: dentro de `doGet`/`doPost` es legítimo —el propio ejemplo oficial de Appian llama a `ServiceLocator.getProcessAnalyticsService2(context)` dentro de `doGet`—, la regla es «no en constructores», no «nunca». El análisis a nivel de método queda fuera de alcance de este escáner, por eso en servlets se delega a la lente de revisión. **Se exige el prefijo `com.appiancorp.`**: «Service Locator» es un nombre de patrón corriente en Java, y sin el prefijo una clase propia como `com.ejemplo.util.DatabaseServiceLocator` dispararía la regla en falso. | En funciones y smart services los servicios se inyectan por constructor o parámetro; usar `ServiceLocator` ahí es motivo de rechazo en la revisión de AppMarket aunque el plugin despliegue y funcione en local. |
| `R-A02` | El bytecode no referencia `java.lang.System` junto con las cadenas `out` o `err` (aproximación a `System.out`/`System.err`). | *AppMarket Submission Policies for Plug-Ins*: *"Logging must be done through Log4j. Do not use `System.out()`, `Exception.printStackTrace()` or similar…"*. | Motivo de rechazo en AppMarket; además el registro no pasa por el pipeline de logs de Appian (rotación, niveles, correlación), y en un entorno compartido esa salida no queda donde el resto de plugins la esperaría. **Heurística declarada, no infalible**: combina «hay `java.lang.System` referenciado» con «hay una cadena `out`/`err` en el pool»; el análisis a nivel de fichero no distingue si vienen de la misma llamada. Falso positivo conocido: una clase que use `System.currentTimeMillis()` (algo inocuo) y además declare un campo o variable llamada `out` o `err`. |
| `R-A03` | El bytecode no referencia la cadena `printStackTrace`. | Misma política que `R-A02`: *"Do not use `System.out()`, `Exception.printStackTrace()` or similar…"*. | Igual que `R-A02`: motivo de rechazo en AppMarket, y la traza vuelca al log combinado de la JVM sin pasar por Log4j, perdiendo nivel y formato. |
| `R-A04` | El bytecode no referencia ningún tipo de acceso directo al sistema de ficheros (`java.io.File`, `FileInputStream`, `FileOutputStream`, `FileReader`, `FileWriter`, `RandomAccessFile`, `java.nio.file.Files`, `java.nio.file.Paths`). | *AppMarket Submission Policies for Plug-Ins*: *"Plug-ins must not manually access or manipulate the file system. Use the `ContentService` and `Document` APIs…"*. | Appian Cloud no garantiza almacenamiento persistente ni compartido en el sistema de ficheros del servidor; motivo de rechazo en AppMarket y fuente de fallos silenciosos si el plugin se ejecuta en un nodo distinto del que escribió el fichero. |
| `R-A05` | El bytecode no **invoca** ninguno de los seis miembros que alteran configuración global de la JVM: `System.setProperty`, `System.setProperties`, `System.clearProperty`, `Locale.setDefault`, `TimeZone.setDefault` y `Security.setProperty`. Como red de seguridad se conserva además una heurística (`java.lang.System` + la cadena `setProperty`) para lo que no genera `Methodref` —una invocación por reflexión—. Un solo hallazgo por clase. | *AppMarket Submission Policies for Plug-Ins*, cita textual: *"Plug-ins must not alter server or JVM global configuration properties (using `System.setProperty()` **or any other method**)"*. Ese «or any other method» es lo que obliga a vigilar más miembros que `System.setProperty`. | Un plugin que altera propiedades globales de la JVM afecta a todos los demás plugins y aplicaciones del mismo servidor Appian; motivo de rechazo en AppMarket. Una clase con solo `Locale.setDefault` y `TimeZone.setDefault` no referencia `java.lang.System`, así que una comprobación apoyada solo en ese tipo la dejaría pasar con 0 hallazgos. **La comprobación exacta NO es heurística**: el par `(tipo, método)` sale de resolver el `Methodref` contra su `CONSTANT_Class`, así que «este tipo, este método» es una sola señal y no dos sueltas — misma fiabilidad que `R-A10`, y por eso la lista puede crecer sin empeorar los falsos positivos. El falso positivo conocido de la heurística sigue ahí, y solo puede darse cuando la exacta no ha disparado. |
| `R-A06` | El bytecode no referencia `java.lang.Class` junto con alguna cadena que empiece por `com.appiancorp.` (indicio de carga dinámica por nombre, vía reflexión, de un tipo de la API de Appian). | Coherencia interna del forge frente a un riesgo que queda abierto: la carga dinámica por cadena (`Class.forName`) evade cualquier análisis estático, y se mitiga —no se resuelve— prohibiendo donde sí se puede comprobar mecánicamente. | La reflexión sobre `com.appiancorp.*` evade el escáner de superficie (capa 2): permite referenciar API no documentada sin que ningún análisis estático lo detecte — exactamente el residuo que queda abierto. **Heurística declarada, no infalible, y la más fina de las tres**: `java.lang.Class` entra en el *constant pool* con cualquier `getClass()`, y el propio patrón de manejo de errores de la plantilla usa `new SmartServiceException.Builder(getClass(), e)`. Basta con que exista en el pool una cadena literal `com.appiancorp.…` —por ejemplo en un mensaje de log— para que salte sin que haya reflexión real. |
| `R-A07` | Si el contrato **no** declara `capacidades.sale_a_la_red = true`, el bytecode no referencia ningún tipo con prefijo `java.net.`, `javax.net.` o `java.nio.channels.Socket` (excepto `java.net.URLEncoder`/`URLDecoder`, de uso interno inofensivo). | *AppMarket Submission Policies for Plug-Ins*: *"Plug-ins must only do what they advertise to do."* La política de red **se deriva del contrato, no está fija en la plantilla** — prohibir `java.net.*` entero es correcto para un lector de correo y falso para un plug-in que deba salir a la red. | Si el bytecode sale a la red sin que el contrato lo declare, el plugin hace algo que su propia documentación no recoge: motivo de rechazo en AppMarket y en la lente de revisión del contrato. |
| `R-A08` | Ninguna cadena del bytecode casa con el patrón de secreto embebido (`password`, `passwd`, `api[_-]?key`, `client[_-]?secret` o `token`, seguido de `:`/`=` y al menos 8 caracteres sin espacio). Incondicional: no depende de que el contrato declare `toca_credenciales`. | *AppMarket Submission Policies for Plug-Ins*: *"Plug-ins must not contain default passwords, authentication keys, key pairs or other credentials for any reason. Use the Secure Credentials Store…"*. | Una credencial embebida en el JAR queda expuesta a quien decompile el plugin — incluido cualquier otro inquilino de un entorno compartido—; motivo de rechazo inmediato en AppMarket. |
| `R-A09` | El `major version` de cada `.class` leído es exactamente 61. | JDK 17, target 17: el servidor de Appian 26.x corre OpenJDK 17 (*System Requirements*: *"The Appian installation includes OpenJDK 17"*) y los 988 `.class` del SDK 26.3 están compilados a *major version* 61, sin excepción — cabeceras de clase leídas una a una. | Un artefacto compilado a una versión de bytecode distinta de la pedida es evidencia de que la verificación de capa 4 no se ejecutó sobre el JAR real, o de que el toolchain no se aplicó como se creía. |
| `R-A10` | El bytecode no referencia, en ninguna cadena del *constant pool*, `getAdministratorServiceContext` ni `getAdministratorUser` (nombres de método de `ServiceLocator`). | *AppMarket Submission Policies for Plug-Ins*: *"The Administrator ServiceContext must not be used."* Firma confirmada con `javap` sobre el JAR del SDK 26.3: `ServiceLocator.getAdministratorServiceContext()` devuelve `com.appiancorp.services.ServiceContext`; `getAdministratorUser()` devuelve `com.appiancorp.suiteapi.personalization.User`. Los nombres de método sí llegan al *constant pool* con cualquier invocación, así que la señal es fiable — a diferencia de las heurísticas de `R-A02`/`R-A05`/`R-A06`. | Un plugin que opera con privilegios de Administrator en vez de con el contexto del usuario que lo invoca es una escalada de privilegios encubierta: motivo de rechazo inmediato en AppMarket, y en producción cualquier usuario que ejecute el plugin obtendría de facto permisos administrativos. |

## Capa 1B (licencias) — copyleft entre las dependencias (`R-L01`–`R-L03`, `scripts/verificar_licencias.py`)

Es la política **más tajante** de toda la página de AppMarket y la única que usa un absoluto,
y su incumplimiento cuesta el rechazo del envío.

**De dónde sale el dato, y por qué no de la red.** `./gradlew build` genera un SBOM CycloneDX
resolviendo el `runtimeClasspath` de verdad; este validador lo **lee**, igual que
`salida_build.py` lee el log de Gradle. Bajarse los POM de Maven Central metería red en tiempo
de verificación, y ningún script del forge la toca hoy.

Que la tarea forme parte de `build` **está cableado a propósito** en la plantilla
(`check.dependsOn cyclonedxDirectBom`). El plugin `org.cyclonedx.bom` 3.3.0 ya la engancha por
su cuenta —se ve con `gradlew build --dry-run`—, pero apoyarse solo en ese comportamiento
dejaba esta puerta dependiendo de un *default* ajeno: si una versión futura dejara de hacerlo,
el camino documentado empezaría a salir rojo sin que nada dijera por qué.

**Límite declarado:** es una comprobación mecánica sobre identificadores SPDX, **no un dictamen
legal**. Cubre lo que el SBOM declara; una dependencia con la licencia mal puesta en su POM se
escapa. Y las familias se comparan sin número de versión a propósito, porque el mismo
identificador llega como `GPL-3.0`, `GPL-3.0-only` o con el nombre largo.

| ID | Qué comprueba | Fuente | Consecuencia si se incumple |
|---|---|---|---|
| `R-L01` | Ninguna dependencia del SBOM usa una licencia copyleft, **fuerte** (`AGPL`, `SSPL`, `OSL`, `EUPL`, `GPL`) o **débil** (`LGPL`, `MPL`, `EPL`, `CDDL`, `CPL`, `CC-BY-SA`). Una licencia **doble** se resuelve por la más restrictiva: elegir la otra es una decisión que un script no puede tomar. | *AppMarket Submission Policies for Plug-Ins*, cita textual: *"Plug-ins must not include **any** third-party libraries licensed under copyleft or similar terms which require software distributed with or linking to those libraries to be distributed under similar terms."* El «or similar terms» es lo que mete al copyleft débil. | **Rechazo del envío.** No es un fallo silencioso ni un aviso: es la política redactada con un absoluto, y quien la aplica es el revisor de Appian. |
| `R-L02` | Toda dependencia del SBOM declara su licencia. | Misma política: no se puede afirmar el cumplimiento sobre una licencia que no consta. | **No se resuelve a favor**, mismo criterio que `UNKNOWN → FAIL` del escáner de superficie: la puerta sale roja hasta que la licencia se declare en el POM o se justifique a mano. |
| `R-L03` | `THIRD_PARTY_NOTICES.md` nombra cada dependencia del SBOM y ya no lleva el `PENDIENTE DE COMPLETAR` que escribe el andamiaje. Solo cuando el SBOM trae al menos una dependencia: sin ninguna, el fichero es correcto tal cual sale. | Política de atribución de terceros de AppMarket; `R-J07` solo mira que el fichero esté dentro del JAR, no lo que dice. | Sin esta regla, un fichero que aún dice «PENDIENTE DE COMPLETAR» pasa las cuatro capas y el certificado da `READY` con la atribución sin cerrar. La licencia la juzga `R-L01`/`R-L02` sobre el SBOM; esta regla solo exige que el documento legible la recoja. |

Nota de alcance: **cero dependencias de terceros es legítimo y frecuente** —el SDK y Log4j son
`compileOnly`, los provee el contenedor—, así que esta puerta **no declara unidad portante**.
Su insumo es el SBOM leído: declarar sólo `dependencias = 0` habría hecho que la regla de
«todas las unidades a cero» marcara como verde vacuo el caso normal, bloqueando el READY de
casi cualquier plug-in. Una alarma que salta siempre enseña a ignorarla.

## Capa 1C — bundles de recursos y locales (`R-B01`–`R-B07`, `scripts/verificar_bundles.py`)

El **bloqueante número uno** de todo el conjunto: sin el bundle `_en_US` correcto, el plug-in no
despliega en absoluto — no es un rechazo de revisión ni un fallo silencioso, es el propio Appian
negándose a cargarlo. Los dos errores más fáciles se acumulan: fichero sin sufijo de locale y
claves de un convenio equivocado. Esta capa comprueba, sobre el **tipo declarado en el contrato**,
cuál de los **dos convenios distintos** de Appian aplica — confundirlos es el error natural, porque
la analogía entre ellos es buena — y la paridad de claves `error.*`/`validation.*` que exige la
internacionalización en cualquier locale que no sea `en_US`.

| ID | Qué comprueba | Fuente | Consecuencia si se incumple |
|---|---|---|---|
| `R-B01` | Existe el bundle `<key-con-puntos-a-separadores>/<nombre-bundle>_en_US.properties`, y cualquier otro `.properties` presente lleva sufijo de locale (`_<xx>_<XX>.properties`). | *Smart Service Plug-ins > Internationalization*, cita textual: *"Plug-ins without a required resource bundle fail to deploy."* La misma página fija nombre y ruta: *"Resource bundle files are named according to the following pattern: `<smart-service@key from appian-plugin.xml>_<locale>.properties`. The bundle file is stored in the package structure where the plugin-key is broken down into a path (by switching dots for path separators)."*, con el ejemplo `/com/example/smart-services/trac-create-ticket_en_US.properties`. Para funciones, *Function Plug-ins > Internationalization* fija la misma carpeta: *"placed in a folder structure based on the plug-in key"*. | El plug-in **no despliega**. Es el bloqueante número uno de todo el conjunto — motivo por el que esta capa existe antes que ninguna otra de empaquetado. |
| `R-B02` | El bundle `_en_US` no mezcla el convenio de claves del otro tipo, **casando siempre por prefijo**: en un smart service, ninguna clave empieza por `smartservice.` ni por `function.`; en una function, ninguna empieza por `input.`, `output.` o `smartservice.`. No se casa por **sufijo** `.description`: las claves `error.*` y `validation.*` pueden terminar en `.description` de forma legítima (p. ej. `error.io.description`) y son justo las que `R-B04` exige, así que casar por sufijo haría que dos reglas del mismo validador se contradijeran. | Appian usa dos convenios distintos: *Function Plug-ins > Internationalization* — `function.<nombre>.description` / `function.<nombre>.param.<Param>.description`, solo en funciones — y *Smart Service Plug-ins > Internationalization > Translation keys* — `name=` / `input.<Name>.displayName` / `.comment` / `output.<Name>.displayName` / `.comment`, solo en smart services. Es el error más fácil de cometer, porque la analogía es buena: una regla cierta en un sitio, ascendida a regla general — el convenio que solo rige en las funciones, trasladado a los smart services. | El fichero tiene el nombre y el locale correctos, pero Appian no encuentra las claves que espera para ese tipo: el efecto observable es el mismo que si las claves obligatorias faltaran (`R-B03`) —displayName/comment, o la descripción de la función, quedan sin proveer—, con la causa oculta detrás de un fichero aparentemente poblado. |
| `R-B03` | El bundle `_en_US` declara TODAS las claves obligatorias del convenio de su tipo, derivadas del propio contrato: `name` + `input.<nombre>.displayName`/`.comment` por cada entrada + `output.<nombre>.displayName`/`.comment` por cada salida en smart services; `function.<nombre-de-función>.description` + `function.<nombre-de-función>.param.<nombre>.description` por cada entrada en functions. | *Smart Service Plug-ins > Internationalization > Translation keys* (formato de smart service: `name`, `input.<InputName>.displayName`, `input.<InputName>.comment`, `output.<OutputName>.displayName`, `output.<OutputName>.comment`) y *Function Plug-ins > Internationalization* (formato de function: `function.functionname.description` y `function.functionname.param.parameterName.description`, con el ejemplo oficial `twitterFunctions_en_US.properties`). | Appian no encuentra el texto de ese campo concreto: el Process Modeler o la paleta de funciones exponen la clave literal (p. ej. `input.documentoOrigen.displayName`) en vez de una etiqueta legible, o el campo queda sin descripción. |
| `R-B04` | Todo bundle de un locale distinto de `en_US` declara las mismas claves `error.*` y `validation.*` que declara `en_US` (paridad; el resto de claves es indiferente porque no se lee). | *Smart Service Plug-ins > Internationalization*, cita textual: *"Currently, only error messages are read from bundles other than the default locale (en_US)."* De ahí que la plantilla haga **obligatorias** en todo locale las claves `error.*` y `validation.*`, y que la paridad se exija en esta capa: un locale sin paridad de claves muestra las claves literalmente al usuario. | El usuario de ese locale ve la clave sin traducir (p. ej. `error.lectura`) en un mensaje de error o de validación, en lugar del texto localizado — degradación silenciosa que solo se detecta probando la interfaz en ese idioma. |
| `R-B05` | **Ningún bundle**, `_en_US` incluido, contiene caracteres no ASCII sin escapar a Unicode (`\uXXXX`). Sin excepción de locale: `_en_US` es precisamente el fichero del que Appian saca los textos de display, o sea el único cuyo mojibake llega a ver un usuario. Por eso la regla recorre los bundles en un **bucle propio**, no dentro del de `R-B04` —que abre con un `continue` sobre el `_en_US` canónico, porque `R-B04` solo habla de los *otros* locales y el bundle más importante no llegaría nunca al predicado—, y ese bucle va **lo primero de `comprobar`**: por debajo del `return` con el que `R-B01` corta cuando el `_en_US` no está en su ruta canónica, un bundle con la tilde cruda no recibiría aviso hasta que se arreglara *otra* regla. | La documentación de Appian exige Unicode escapado en los bundles de los plug-ins de componente —*Configuration Files > Internationalization bundles > Unicode properties*: *"Property values for languages with unicode characters (… and any characters with character accents) need to be specified using escaped unicode. If they are not, the translations do not render properly on Appian."*— y de sistema conectado (*Support Multiple Languages*, con el mismo aviso). Las páginas de function y smart service no dicen nada distinto. | **Aviso, no error**: no hay evidencia confirmada de que un `.properties` en UTF-8 sin escapar rompa el despliegue de una function o un smart service, solo de que se aparta de la convención documentada; queda como aviso mientras no se confirme si el cargador de bundles de Appian exige estrictamente `\uXXXX`. |
| `R-B06` | **En smart services**, ninguna clave `input.*` / `output.*` del bundle `_en_US` que no corresponda a una entrada o salida real. El conjunto admitido son las claves derivadas del contrato (las mismas de `R-B03`) **más** las de las dos salidas horneadas (`ErrorOccurred`, `ErrorMessage`), que la plantilla declara siempre aunque el contrato no las enumere. Cuando la clave sobrante es una admitida con otra caja, el mensaje **sugiere la correcta**. | Appian expone el output por el **accesor**, no por el campo. *Smart Service Plug-ins > Internationalization > Translation keys*: *"`InputName` and `OutputName` are the camelCase names (or `@Name` annotated names) of the targets of the getter and setter methods (after removing the prepended `get-` or `set-`)."* Así que `getErrorOccurred()` publica el output `ErrorOccurred` (mismo fundamento que `contrato.identificador_java`), y una plantilla que hornease `output.errorOccurred.*` en minúscula pasaría todas las demás reglas. | La clave no etiqueta nada: el Process Modeler muestra el output sin nombre legible. **No impide desplegar, y ninguna otra regla lo ve**: `R-B03` compara `esperadas − presentes` —solo lo que falta— y la clave sobrante no casa con ningún prefijo prohibido de `R-B02`. Era el hueco por el que una comprobación unidireccional se daba la razón a sí misma. |
| `R-B07` | **Un bundle `_en_US` por cada módulo declarado en `appian-plugin.xml`**, llamado como la `key` de ese módulo y en la carpeta que sale de la `key` del plug-in: `<key-del-plug-in-con-puntos-a-separadores>/<key-del-módulo>_en_US.properties`, por cada `<function>` y cada `<smart-service>`. Es la única regla de la capa que lee el **manifiesto** en vez del contrato, y por eso ve lo que las demás no pueden ver: el contrato describe **un** módulo, así que un manifiesto con varios —escrito a mano, o ampliado después de andamiar— deja módulos sin bundle sin que nada lo note. `R-B01` deriva su ruta de `bundle.nombre`, o sea que sus dos lados salen del mismo dato y coinciden aunque el manifiesto diga otra cosa. Va **antes** del `return` de `R-B01`, junto a `R-B05`, porque solo mira rutas: por debajo no se enteraría de los módulos sin bundle cuando además falta el del contrato. | *Function Plug-ins > Internationalization*: *"Internationalization bundles for function names, parameter names, and descriptions are by default placed in a folder structure based on the plug-in key."* La misma página fija que la `key` nombra el **módulo** y no la función: su ejemplo oficial es un solo bundle `twitterFunctions_en_US.properties` con las claves de dos funciones, `function.twittertrends.description` y `function.twittersearch.description`. Para smart services el patrón es explícito en *Smart Service Plug-ins > Internationalization*: *"Resource bundle files are named according to the following pattern: `<smart-service@key from appian-plugin.xml>_<locale>.properties`"*. Y el propio servidor lo dice al rechazar el despliegue: *"The Plug-in `<key>` Module `<key del módulo>` is missing the following internationalization bundle(s) for Locale en_US: `[<key>.<key del módulo>]` (APNX-1-4200-000)"*. | El plug-in **no despliega**, y Appian se detiene en el **primer** módulo sin bundle: los siguientes ni se comprueban, así que un solo módulo mal nombrado impide cargar todo el plug-in. Ninguna otra regla lo ve. |

Nota de alcance: los plugins `tipo = "servlet"` quedan fuera de esta capa — su `name`/`description`
se declaran directamente como atributos del elemento `<servlet>` en `appian-plugin.xml`, no en un
`.properties`, así que no hay bundle que comprobar.

## Capa 4 — empaquetado del JAR y cierre de dependencias (`R-J01`–`R-J09`, `scripts/verificar_jar.py`)

Compilar y testear no dice nada de lo que finalmente se entrega: esta capa mira el **JAR ya
construido**, no el árbol de fuentes ni el classpath de Gradle. Se hace en Python, fuera de Gradle,
para que sea la misma herramienta en las cuatro capas. Lo que esta capa **no** cubre, y se declara en
el certificado: la resolución OSGi real de la plataforma — el cierre de dependencias (`R-J05`) atrapa
el fallo más probable, una clase que falta, pero no un conflicto de versiones con lo que Appian ya
carga.

| ID | Qué comprueba | Fuente | Consecuencia si se incumple |
|---|---|---|---|
| `R-J01` | `appian-plugin.xml` existe en la **raíz** del JAR (no en ninguna subcarpeta, incluida `META-INF/`). | *Appian Suite Plug-ins > Plug-in manifest (appian-plugin.xml)*, cita textual: *"Every Appian Plug-in must have an `appian-plugin.xml` at the root of the Plug-in jar. If this file is not present, the Plug-in is ignored."* | Appian no encuentra el descriptor: el plug-in no despliega. Mismo fallo que evita `R-B01`, aquí comprobado sobre el artefacto final en vez de sobre el árbol de resources — cubre el caso en que el fichero exista en el proyecto pero el build lo coloque mal. |
| `R-J02` | El JAR contiene al menos un fichero `.java` bajo `src/` (fuente embebida). | *AppMarket Submission Policies for Plug-Ins*, cita textual: *"Plug-ins must include the source code within the executable."* | Rechazo en la revisión de AppMarket / Appian Cloud: el criterio de aceptación exige la fuente dentro del propio entregable, no en un repositorio aparte. |
| `R-J03` | El JAR no contiene ninguna entrada que termine en `Test.class`/`Test.java`, ni ninguna bajo `fixtures/`. | Coherencia interna del forge: el entregable no lleva clases ni fixtures de test (`**/*Test.class`, `**/*Test.java`, `fixtures/**`). | El entregable expone código y datos de prueba internos — superficie extra sin valor para quien lo instala, y motivo de rechazo por higiene de empaquetado si AppMarket lo revisa. |
| `R-J04` | Ninguna entrada de `META-INF/lib/*.jar` contiene `appian-plug-in-sdk` ni empieza por `log4j-`. | El JAR del SDK 26.3, inspeccionado con `jar tf`, no contiene ni `org/apache/log4j` ni `javax/servlet`: son librerías aparte que provee el contenedor. Ambas dependencias, y el propio SDK, se declaran `compileOnly` desde Maven Central (*"The Suite API SDK is available on Maven Central… Add it as a dependency"*), y no deben acabar empaquetadas en `META-INF/lib`. | Conflicto de carga de clases (dos copias del mismo tipo en classloaders distintos): la razón por la que el propio Appian marca ambas dependencias `compileOnly` en su `build.gradle` oficial. |
| `R-J05` | Toda dependencia esperada tiene un `.jar` homónimo dentro de `META-INF/lib`. La lista sale **del propio contrato** (`dependencias`, traducidas `grupo:artefacto:versión` → `artefacto-versión.jar`, que es como Gradle nombra lo que copia); los argumentos sueltos de la CLI **añaden** transitivas, no sustituyen. Una lista que saliera solo de la CLI llegaría vacía con el comando documentado y la regla pasaría por vacuidad; por eso el validador **declara cuántas dependencias comprobó**, incluido «ninguna», para que la evidencia del certificado no pueda confundirse con «comprobado y correcto». Alcance: dependencias directas del contrato, no transitivas — el inventario completo es el SBOM. | Coherencia interna del forge: cada dependencia `implementation` —y sus transitivas— tiene que estar en `META-INF/lib`, que es donde el `build.gradle` copia el `runtimeClasspath`. Es lo que evita un `NoClassDefFoundError` que solo aparecería tras el despliegue. | `NoClassDefFoundError` en tiempo de ejecución, **después** de desplegar — el fallo que más tarde se detecta de toda la cadena, porque compilar y testear en local no lo revela. |
| `R-J06` | **Cada módulo declarado en el `appian-plugin.xml` que viaja dentro del JAR** tiene su bundle `<key-del-plug-in-con-puntos-a-separadores>/<key-del-módulo>_en_US.properties` dentro del mismo JAR. La lista de módulos sale del manifiesto **empaquetado**, que es el fichero que leerá Appian, no del árbol de `resources` ni del contrato: es la comprobación más fiel que puede hacerse sin un servidor delante. Si el JAR no lleva manifiesto, la regla lo dice en rojo en vez de callar. | Mismo fundamento que `R-B07`, verificado aquí sobre el **artefacto ya construido** en vez de sobre el árbol de resources. | El plug-in no despliega, aunque `R-B07` no hubiera encontrado ningún problema antes de construir el JAR — cubre el caso en que el bundle exista en `resources/` pero el build no lo empaquete. |
| `R-J07` | `META-INF/LICENSE` y `META-INF/THIRD_PARTY_NOTICES.md` están presentes dentro del JAR. | Coherencia interna del forge, en apoyo de la política de librerías y licencias de *AppMarket Submission Policies for Plug-Ins* (*"Plug-ins must have full rights to use and distribute all code or libraries…"*). | Incumplimiento de la política de atribución de terceros de AppMarket; motivo de rechazo en la revisión. Alcance de esta regla: solo presencia — lo que el fichero dice lo juzga `R-L03`, y la licencia de cada dependencia, `R-L01`/`R-L02` sobre el SBOM. |
| `R-J08` | El JAR no tiene dos entradas con el mismo nombre. | Coherencia interna del forge: un ZIP con dos entradas del mismo nombre es ambiguo, y ninguna herramienta garantiza cuál de las dos gana. | Comportamiento no determinista sobre qué entrada gana al desempaquetar o cargar la clase — una fuente de bugs difíciles de reproducir porque depende de qué herramienta lee el ZIP. |
| `R-J09` | El JAR pesa 15 MB o menos. | **No hay límite documentado por Appian** para el tamaño de un plug-in; es un umbral operativo propio del forge, sin fuente oficial. | Sin evidencia de que Appian rechace un JAR por tamaño; el tope es una guarda de higiene propia — un JAR inesperadamente grande suele delatar una dependencia de más, un recurso embebido por error, o el propio SDK colado dentro (véase `R-J04`). |

Nota de alcance: `R-J01`–`R-J09` solo se pueden ejecutar sobre un JAR ya construido — a diferencia de
las capas 1A/1B/1C, que corren contra el contrato, el manifiesto o las clases sueltas antes de
empaquetar.
